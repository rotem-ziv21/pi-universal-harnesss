# התקנה בסביבה חיצונית — RunPod

מדריך להתקנת ה‑Harness על פוד שכבר מותקן בו Pi.

---

## הדבר האחד שחייבים להבין לפני שמתחילים

ב‑RunPod רוב מערכת הקבצים **נמחקת בכל הפעלה מחדש של הפוד**. מה ששורד הוא רק ה‑Network Volume — בדרך כלל מותקן תחת נתיב קבוע כמו workspace.

ל‑Pi ול‑Harness יש שלושה דברים שאתה רוצה שישרדו:

הקוד של ה‑Harness — הריפו עצמו

הקונפיגורציה של Pi — כולל תיקיית התוספים

ה‑state של ה‑Harness — חוזי משימה, יומני ביקורת, המפתח המקומי

אם תתקין הכול תחת תיקיית הבית ברירת המחדל, הכול יימחק באתחול הבא ותצטרך להתקין מחדש בכל פעם. **המדריך הזה מתקין הכול על הווליום הקבוע.**

---

## שלב אפס — מה מותקן אצלך

התחבר לפוד ותבדוק:

```bash
pi --version        # צריך להיות 0.85 ומעלה
node --version      # צריך להיות 22.19 ומעלה
echo $HOME
df -h | grep -i workspace   # לוודא שיש ווליום קבוע ואיפה הוא
```

אם אין ווליום קבוע, המדריך עדיין יעבוד — פשוט תדלג על החלק של הנתיבים הקבועים ותדע שתצטרך להתקין מחדש אחרי כל אתחול.

---

## שלב אחד — משיכת הקוד

הריפו **פרטי**, אז שיבוט אנונימי ייכשל. שתי דרכים:

### אפשרות א — טוקן אישי (הכי פשוט לפוד)

צור טוקן ב‑GitHub תחת Settings ואז Developer settings ואז Personal access tokens, עם הרשאת קריאה לריפו בלבד.

```bash
cd /workspace
git clone https://<TOKEN>@github.com/rotem-ziv21/pi-universal-harnesss.git
cd pi-universal-harnesss
```

שים לב: הטוקן נשמר בתוך כתובת ה‑remote בתיקיית הגיט. אם זה מפריע לך, נקה אחרי השיבוט:

```bash
git remote set-url origin https://github.com/rotem-ziv21/pi-universal-harnesss.git
```

### אפשרות ב — מפתח פריסה

צור מפתח SSH על הפוד, הוסף אותו כ‑Deploy Key בהגדרות הריפו, ושבט דרך SSH. עדיף אם הפוד ארוך טווח.

## שלב שתיים — הפניית Pi לווליום הקבוע

זה החלק שהופך את ההתקנה לעמידה מול אתחולים.

ל‑Pi יש משתנה סביבה רשמי שקובע איפה תיקיית הסוכן שלו יושבת. אימתתי את זה בקוד המקור של הגרסה שמותקנת אצלך — Pi משתמש בתיקיית הבית, ומכבד את המשתנה הזה כעקיפה:

```bash
export PI_CODING_AGENT_DIR=/workspace/.pi/agent
```

ול‑state של ה‑Harness יש משתנה משלו:

```bash
export PI_HARNESS_HOME=/workspace/.pi/agent/harness
```

וגם המפתח:

```bash
export OPENROUTER_API_KEY="sk-or-v1-..."
```

כדי שזה ישרוד אתחול, שים את שלושת השורות האלה בקובץ על הווליום ותטען אותו מהפרופיל:

```bash
mkdir -p /workspace/.pi
cat > /workspace/pi-env.sh <<'EOF'
export PI_CODING_AGENT_DIR=/workspace/.pi/agent
export PI_HARNESS_HOME=/workspace/.pi/agent/harness
export OPENROUTER_API_KEY="sk-or-v1-..."
EOF
chmod 600 /workspace/pi-env.sh

echo '[ -f /workspace/pi-env.sh ] && . /workspace/pi-env.sh' >> ~/.bashrc
. /workspace/pi-env.sh
```

### הערה חשובה על המפתח

אם אתה מגדיר את המפתח דרך תבנית הפוד ב‑RunPod — מה שעדיף — אל תשים אותו גם בקובץ. משתנה הסביבה תמיד גובר על המחסן המקומי, וזה בכוונה.

**אל תשים את המפתח בקובץ שיושב בתוך הריפו.** הקובץ למעלה יושב מחוץ לריפו, וזה מכוון.

## שלב שלוש — התקנה

```bash
cd /workspace/pi-universal-harnesss
./scripts/install.sh --dry-run    # קודם להסתכל
./scripts/install.sh              # ואז באמת
```

המתקין מגלה הכול בזמן ריצה: מערכת ההפעלה, גרסת Node, מיקום Pi וגרסתו, ואת שם תיקיית הקונפיג — שאותו הוא קורא מהחבילה **המותקנת** של Pi במקום להניח.

הוא יוצר קישור סימבולי מהריפו לתיקיית התוספים, לא העתק. זה אומר שעדכון עתידי הוא רק משיכה מגיט.

---

## שלב ארבע — אימות

```bash
./scripts/doctor.sh
```

ואז בתוך Pi:

```
pi
/harness doctor
```

מה שאתה רוצה לראות:

תוסף מותקן — עובר

תיקיית state — ניתנת לכתיבה, ועל הווליום הקבוע

מפתח OpenRouter — מוגדר

קישוריות לשופט — עובר

אם הקישוריות נכשלת, ההודעה תגיד בדיוק למה ומה לעשות. כל כשל במאבחן מגיע עם תיקון מוצהר.

## הסרה

```bash
./scripts/uninstall.sh                 # מסיר את התוסף, שומר את ההיסטוריה
./scripts/uninstall.sh --purge-state   # מוחק גם קונפיג, סודות והיסטוריה
```

המסיר נוגע רק במה שהוא התקין. הוא לא ייגע ב‑Pi, בתוספים אחרים, בקבצי פרויקט או בקונפיגורציה שהוא לא יצר. מחיקת היסטוריה דורשת אישור מפורש בהקלדה.

## באג שתוקן בזכות השאלה הזאת

כשבדקתי איך Pi באמת מאתר את תיקיית הקונפיג שלו, גיליתי טעות בקוד שלי.

ה‑Harness התחשב במשתנה הסביבה התקני של לינוקס לתיקיות קונפיג. **Pi לא מתחשב בו.** Pi משתמש בתיקיית הבית ובמשתנה העקיפה הייעודי שלו בלבד.

המשמעות הייתה חמורה דווקא בסביבות כמו RunPod, שבהן המשתנה הזה מוגדר לעיתים קרובות בתמונת הקונטיינר: המתקין היה יוצר את הקישור בתיקייה ש‑Pi לעולם לא קורא ממנה. ההתקנה הייתה מדווחת על הצלחה, המאבחן היה מדווח על הצלחה, ו**התוסף פשוט לא היה נטען** — בלי שום הודעת שגיאה.

זה תוקן בשלושת הסקריפטים ובקוד, והפתרון עכשיו תואם בדיוק את מה שאימתתי בקוד המקור של Pi.

## תקלות נפוצות

**התוסף לא נטען ואין שגיאה**

תבדוק שהנתיב שהמתקין הדפיס הוא באמת מה ש‑Pi קורא:

```bash
echo $PI_CODING_AGENT_DIR
ls -la ${PI_CODING_AGENT_DIR:-$HOME/.pi/agent}/extensions
```

**הכול נמחק אחרי אתחול הפוד**

סימן שההתקנה לא ישבה על הווליום הקבוע. תחזור לשלב שתיים.

**השופט לא זמין**

זה לא עוצר אותך — המערכת נופלת לשופט המודל ואז לדטרמיניסטי. אבל הדטרמיניסטי לעולם לא מאשר פעולה קריטית, אז תיתקל בהרבה בקשות אישור. תפעיל את המאבחן כדי לראות מה חסר.

**הרשאות על מחסן הסודות**

המאבחן נכשל אם הקובץ קריא לקבוצה או לעולם. התיקון מודפס בשורה שמתחת לכשל.

## למה זה עובד אותו דבר בכל מקום

שום נתיב ספציפי למכונה לא מקודד בקוד. לא תיקיית בית, לא ווליום, לא כרטיס מסך, לא נקודת קצה ולא פרויקט. הכול מתגלה בזמן ריצה, ולכל שלב יש עקיפה מפורשת דרך משתנה סביבה.

**הקוד עובר בגיט. הסודות לא.** אותו ריפו בדיוק רץ על המק, על הפוד ועל כל מכונה עתידית — כשההבדל היחיד הוא מפתח מקומי שאף פעם לא נכנס לגיט.
